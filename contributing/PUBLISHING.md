# Publishing a Registry Package

A registry package is an npm package that adds addons, adapters, frameworks or templates to Forge. A project picks one up with `forge add @scope/name`, which installs it as a devDependency and records it in `.forge/manifest.json`.

This guide follows [`examples/registry-package`](../examples/registry-package), which teaches the first-party Vitest addon to work with Next.js. The registry smoke test installs that package on every run, so every code block below is copied from a package that is known to load.

## Manifest

A registry package has two parts: its `package.json` and the object its entry point exports by default.

```json
{
	"name": "@example/forge-registry",
	"version": "0.1.0",
	"type": "module",
	"exports": {
		".": "./index.mjs"
	},
	"files": [
		"index.mjs"
	],
	"dependencies": {
		"effect": "4.0.0-rc.117"
	}
}
```

The package name is the registry id, and it must be scoped. `forge add` only treats a scoped name it does not already know as a registry package.

The `version` field is required. Forge stores it in the manifest and compares it on every `forge update`.

Every `contribute` function returns an Effect, so `effect` is a runtime dependency. The example pins the Effect version Forge is built with, and the smoke test fails when the two drift apart.

The default export describes everything the package provides:

```js
export default {
	apiVersion: 1,
	adapters: [adapter],
	catalog: [],
};
```

- `apiVersion` is the authoring API the package targets. This release of Forge accepts `1` and nothing else.
- `catalog` is required, even when it is empty. It holds the entries `forge list` and `forge info` show for the addons, frameworks and templates the package defines. An adapter for an addon that already exists needs no entry.
- `addons`, `adapters`, `frameworks` and `templates` are optional arrays of units.

Addon, framework, template and catalog ids must be scoped as well, such as `@example/sentry`. Adapters have no id of their own: Forge keys them by the addon and framework they join.

Units are plain objects tagged with `_tag`. This is the example's adapter:

```js
const adapter = {
	_tag: "AdapterDefinition",
	addon: "vitest",
	framework: "nextjs",
	requiredSlots: [],
	contribute: ({ module }) =>
		Effect.succeed([
			{
				_tag: "LeafTextFileContribution",
				target: {
					_tag: "ResolvedModuleTarget",
					moduleId: module.id,
					moduleRoot: module.root,
				},
				path: "registry-adapter.txt",
				content: "Generated by the example registry.\n",
			},
		]),
};
```

`addon` and `framework` must name units that are already registered, either first party or from a registry listed earlier in the project. `requiredSlots` lists the framework slots the adapter writes into. `contribute` receives the project config, the framework, the target module and its slots, and returns an Effect that yields a list of contributions. A `LeafTextFileContribution` writes one file inside the module. The full set of unit fields and contribution tags is defined in `packages/core/src/authoring.ts`.

## Exports

Forge resolves the package from the project root the way Node does, then imports its entry point.

- The root export is the only one Forge reads. Subpath exports are ignored.
- Forge first resolves the root export the way `require` would.
- An ESM only package, whose root export has only an `import` condition, still loads. When CommonJS resolution refuses the package, Forge reads the root export itself: a string, an object of conditions or an array of alternatives, preferring `import`, then `default`, then the first nested condition that resolves.
- A package with no `exports` field loads through `main`.
- The manifest must be the default export. A CommonJS build loads whether it assigns the manifest to `module.exports` or to `module.exports.default`, because Forge unwraps one nested `default`.

## Errors

Forge stops at the first problem it finds and names the registry in the message.

- `Registry Not Installed: <id>` means the package does not resolve from the project root. Install it as a devDependency of the project, or let `forge add` install it.
- `Registry Package Version Missing: <id>` means the package's `package.json` has no `version` field.
- `Registry Import Failed: <id>: <detail>` means the entry point threw while it was being imported. The detail is the original error.
- `Registry Package Invalid: <id>` means the default export does not match the manifest shape, or a unit is missing a field, has a field of the wrong type, or has a `contribute`, `when` or `target` that is not a function.
- `Registry Api Version Unsupported: <id> expected 1, found <n>` means `apiVersion` is not one this Forge release understands.
- `Registry Unit Id Invalid: <id>` means an addon, framework, template or catalog id is not scoped.
- `Registry Catalog Duplicate: <id>` means a catalog id is already taken by Forge or by another registry.
- `Registry Duplicate: <id>` means the project lists the same registry twice.

Once the shapes are valid, Forge registers the units together with everything already loaded. A conflict there surfaces as the registration error itself:

- `Addon Duplicate: <id>`, `Framework Duplicate: <id>` and `Template Duplicate: <id>` mean the id is already registered.
- `Adapter Duplicate: <addon>:<framework>` means another adapter already joins that addon and framework.
- `Adapter Addon Missing: <addon>` and `Adapter Framework Missing: <framework>` mean the adapter names a unit that is not registered.
- `Adapter Slot Missing: <addon>:<framework>:<slot>` means `requiredSlots` names a slot the framework does not declare.
- `Framework Slots Invalid: <id>` means a framework declares no slots, an empty slot name, or the same slot twice.

## Releasing an update

Bump `version` in `package.json` and publish the package the usual way. Forge never checks npm for new releases on its own.

A project moves to the new release when its owner upgrades the dependency with their package manager and runs `forge update`. Forge reloads every registry, reconciles the files it manages, records the new version in `.forge/manifest.json`, and prints one line for each registry whose version changed:

`@example/forge-registry 0.1.0 -> 0.2.0.`

The registry smoke test runs exactly this upgrade against the example package.

Projects apply whatever the installed release generates, so treat a change to generated output like any other change to your package. Removing or renaming a unit that projects already use is a breaking change and calls for a major version.
